## 설계 개요

| 클래스 | 역할 | 핵심 속성·메서드 |
|---|---|---|
| `Item` | 키와 값 한 쌍을 담는 항목 | `key`, `value` |
| `HashTable` | 정해진 개수의 버킷에 항목을 나눠 저장하는 해시 맵 | `size`, `table`, `_hash_function()`, `set()`, `get()`, `remove()` |

- **저장 구조**: `table`은 `size`개의 빈 리스트로 시작합니다. 리스트 하나하나가 버킷이고, 같은 버킷으로 해시된 `Item`이 그 안에 차례로 쌓입니다. 이것이 체이닝입니다.
- **해시 함수**: `_hash_function()`은 `key % self.size`로 버킷 인덱스를 구합니다. 키가 정수라는 가정 덕분에 나머지 연산 하나로 충분합니다.
- **`set()`**: 해당 버킷을 훑어 같은 키가 있으면 값만 덮어쓰고 끝냅니다. 없으면 새 `Item`을 버킷 끝에 추가합니다. 그래서 같은 키가 두 번 저장되지 않습니다.
- **`get()`과 `remove()`**: 둘 다 해당 버킷을 처음부터 훑습니다. 키를 찾으면 값을 돌려주거나(`get`) 버킷에서 그 항목을 지우고(`remove`), 끝까지 찾지 못하면 `KeyError('Key not found')`를 던집니다.
- **의도적인 단순화**: 적재율을 신경 쓰지 않는다는 가정에 따라, 항목이 아무리 늘어도 버킷 수를 늘리는 리사이징(resizing)이나 재해싱(rehashing)은 하지 않습니다. 한편 다른 OOD 문제와 달리 이 코드에는 `pass`로 비워 둔 메서드가 없고, 모든 메서드가 끝까지 구현되어 있습니다.

## 면접에서는

- **제약 조건부터 확인하세요.** 키의 타입, 충돌 해결 방식, 적재율 고려 여부, 입력 검증, 메모리 크기를 물어 범위를 좁힙니다. 이 문제의 제약 조건 목록이 그대로 좋은 질문 목록입니다.
- **핵심 객체는 둘이면 충분합니다.** 키·값 쌍(`Item`)과 이를 담는 테이블(`HashTable`)입니다. 객체를 늘리기보다 버킷 구조와 해시 함수를 분명하게 설명하는 데 시간을 쓰세요.
- **관계와 트레이드오프를 말하세요.** 테이블은 버킷 리스트를, 버킷은 `Item`을 담습니다. 체이닝은 구현이 단순하지만, 한 버킷에 항목이 몰리면 그 버킷을 선형 탐색하는 시간이 길어진다는 대가가 있습니다.
- **확장 포인트를 짚어 두세요.** 적재율 제약이 풀리면 항목 수를 세다가 임계값을 넘을 때 버킷을 늘리고 모든 항목을 다시 해시해야 합니다. 정수가 아닌 키를 받으려면 키를 먼저 정수로 바꾸는 해시 함수가 필요합니다.
- 시스템 설계 면접에서 만나는 [키-값 저장소](/topics/database/nosql/#키-값-저장소-key-value-store)는 해시 테이블을 추상화한 것으로, 보통 O(1) 읽기·쓰기를 제공합니다. Memcached나 Redis 같은 인메모리 캐시도 키-값 저장소입니다. ([캐시](/topics/cache/#애플리케이션-캐싱-application-caching) 참고)

## 스스로 점검하기

<details>
<summary>set, get, remove의 시간 복잡도는 어떻게 되나요?</summary>

세 연산 모두 해시 함수 계산(O(1)) 뒤에 버킷 하나를 선형 탐색합니다. 키가 버킷에 고르게 퍼지면 버킷 길이는 평균 `n / size` 정도이므로 평균 `O(1 + n / size)`이고, 버킷 수에 비해 항목 수가 적당하면 O(1)로 봅니다. 모든 키가 한 버킷에 몰리면 최악 O(n)입니다. 이 코드는 리사이징을 하지 않으므로 `size`보다 훨씬 많은 항목을 넣으면 평균 탐색 시간도 그만큼 길어집니다.

</details>

<details>
<summary>같은 키로 set을 두 번 호출하면 어떻게 되나요?</summary>

`set()`은 먼저 버킷에서 같은 키를 찾습니다. 찾으면 그 `Item`의 값만 새 값으로 바꾸고 반환하므로, 버킷에는 해당 키의 항목이 하나만 남습니다.

</details>

<details>
<summary>적재율을 고려하라는 요구가 추가되면 무엇을 바꿔야 하나요?</summary>

저장된 항목 수를 세는 필드를 두고, `set()`으로 새 항목을 추가한 뒤 "항목 수 / 버킷 수"가 임계값을 넘으면 더 큰 `table`을 만들어야 합니다. 이때 `_hash_function()`이 `self.size`에 의존하므로 버킷 수가 바뀌면 기존 인덱스가 모두 달라집니다. 따라서 모든 `Item`을 새 `size` 기준으로 다시 해시해 옮겨야 합니다.

</details>

<details>
<summary>키가 문자열이라면 무엇을 바꿔야 하나요?</summary>

`key % self.size`는 정수에서만 동작하므로, 키를 먼저 정수로 바꾸는 해시 함수가 필요합니다(예: 파이썬의 `hash(key) % self.size`). 버킷 안에서 `item.key == key`로 키를 비교하는 부분은 그대로 쓸 수 있습니다.

</details>
