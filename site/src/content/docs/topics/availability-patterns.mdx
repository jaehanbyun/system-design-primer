:::note[핵심 요약]
- 고가용성을 지원하는 두 가지 상호 보완적인 패턴은 **장애 조치**(fail-over)와 **복제**(replication)입니다.
- **액티브-패시브**에서는 액티브 서버만 트래픽을 처리하고, 하트비트가 끊기면 대기 중인 패시브 서버가 액티브 서버의 IP를 넘겨받습니다. **액티브-액티브**에서는 두 서버가 모두 트래픽을 처리합니다.
- 장애 조치는 하드웨어와 복잡도를 늘리고, 새로 쓴 데이터가 복제되기 전에 액티브 시스템이 실패하면 데이터를 잃을 수 있습니다.
- 가용성은 보통 9의 개수로 표현합니다. 99.9%는 연간 8시간 45분 57초, 99.99%는 연간 52분 35.7초의 다운타임을 허용합니다.
- 가용성이 100% 미만인 구성 요소를 **직렬**로 연결하면 전체 가용성이 낮아지고, **병렬**로 연결하면 높아집니다.
:::

고가용성을 지원하는 상호 보완적인 패턴이 두 가지 있습니다. 바로 **장애 조치**(fail-over)와 **복제**(replication)입니다.

## 장애 조치 (Fail-over)

### 액티브-패시브 (Active-passive)

액티브-패시브 장애 조치에서는 액티브 서버와 대기(standby) 중인 패시브 서버가 하트비트(heartbeat)를 주고받습니다. 하트비트가 끊기면 패시브 서버가 액티브 서버의 IP 주소를 넘겨받아 서비스를 재개합니다.

다운타임이 얼마나 길어질지는 패시브 서버가 이미 실행 중인 '핫(hot)' 대기 상태인지, 아니면 새로 시작해야 하는 '콜드(cold)' 대기 상태인지에 따라 달라집니다. 트래픽은 액티브 서버만 처리합니다.

액티브-패시브 장애 조치는 마스터-슬레이브 장애 조치라고도 부릅니다.

### 액티브-액티브 (Active-active)

액티브-액티브에서는 두 서버가 모두 트래픽을 처리하며 부하를 나눠 가집니다.

서버가 외부에 공개되어 있다면 DNS가 두 서버의 공인 IP를 모두 알고 있어야 합니다. 서버가 내부용이라면 애플리케이션 로직이 두 서버를 모두 알고 있어야 합니다.

액티브-액티브 장애 조치는 마스터-마스터 장애 조치라고도 부릅니다.

:::caution[단점: 장애 조치]
- 장애 조치를 하려면 하드웨어가 더 필요하고 복잡도도 늘어납니다.
- 새로 쓰인 데이터가 패시브 시스템으로 복제되기 전에 액티브 시스템이 실패하면 데이터를 잃을 수 있습니다.
:::

## 숫자로 보는 가용성 (Availability in numbers)

가용성은 흔히 서비스를 이용할 수 있는 시간의 비율, 즉 업타임(또는 다운타임) 비율로 수치화합니다. 가용성은 보통 9의 개수로 측정하는데, 가용성이 99.99%인 서비스는 '9가 네 개(four 9s)'라고 표현합니다.

### 99.9% 가용성: 9가 세 개 (three 9s)

| 기간 | 허용 가능한 다운타임 |
|---|---|
| 연간 다운타임 | 8시간 45분 57초 |
| 월간 다운타임 | 43분 49.7초 |
| 주간 다운타임 | 10분 4.8초 |
| 일간 다운타임 | 1분 26.4초 |

### 99.99% 가용성: 9가 네 개 (four 9s)

| 기간 | 허용 가능한 다운타임 |
|---|---|
| 연간 다운타임 | 52분 35.7초 |
| 월간 다운타임 | 4분 23초 |
| 주간 다운타임 | 1분 5초 |
| 일간 다운타임 | 8.6초 |

:::note[원문 표의 주간 값 바로잡기]
원문은 99.99%의 주간 다운타임을 `1m 5s`로 적고 있지만, 실제로 계산하면 1주(604,800초)의 0.01%인 약 60.5초(1분 0.5초)입니다. 표는 원문 그대로 두었고, 아래 계산기는 계산한 값을 보여 줍니다.
:::

### 병렬 vs 직렬 구성의 가용성 (Availability in parallel vs in sequence)

서비스가 장애가 날 수 있는 여러 구성 요소로 이루어져 있다면, 서비스의 전체 가용성은 그 구성 요소들이 직렬로 연결되어 있는지 병렬로 연결되어 있는지에 따라 달라집니다.

#### 직렬 구성 (In sequence)

가용성이 100% 미만인 두 구성 요소를 직렬로 연결하면 전체 가용성은 낮아집니다.

```
Availability (Total) = Availability (Foo) * Availability (Bar)
```

`Foo`와 `Bar`의 가용성이 각각 99.9%라면, 둘을 직렬로 연결했을 때 전체 가용성은 99.8%가 됩니다.

#### 병렬 구성 (In parallel)

가용성이 100% 미만인 두 구성 요소를 병렬로 연결하면 전체 가용성은 높아집니다.

```
Availability (Total) = 1 - (1 - Availability (Foo)) * (1 - Availability (Bar))
```

`Foo`와 `Bar`의 가용성이 각각 99.9%라면, 둘을 병렬로 연결했을 때 전체 가용성은 99.9999%가 됩니다.

## 면접에서는

- 단일 장애 지점(SPOF)을 없애는 방법으로 장애 조치와 복제를 함께 제안하세요. [AWS에서 수백만 사용자로 확장하기](/system-design/scaling-aws/) 해설은 로드 밸런서를 직접 구성할 때 여러 가용 영역(availability zone)에 액티브-액티브나 액티브-패시브로 두고, MySQL을 마스터-슬레이브 장애 조치 구성으로 여러 가용 영역에 배치해 가용성과 이중화를 높입니다.
- 액티브-패시브를 제안한다면 핫 대기인지 콜드 대기인지에 따라 다운타임이 달라진다는 점을, 액티브-액티브를 제안한다면 DNS나 애플리케이션 로직이 두 서버를 모두 알아야 한다는 점을 함께 말하세요.
- 장애 조치의 비용도 빠뜨리지 마세요. 하드웨어와 복잡도가 늘고, 복제가 끝나기 전에 액티브 시스템이 실패하면 데이터를 잃을 수 있습니다.
- 가용성 목표는 9의 개수로 말하고, 그것이 허용 다운타임으로 얼마인지 환산해 보이면 설득력이 생깁니다. 99.9%와 99.99%는 연간 다운타임이 약 8시간 46분과 약 53분으로 크게 차이 납니다.
- 요청 경로에 구성 요소를 직렬로 늘릴수록 전체 가용성은 낮아지고, 같은 구성 요소를 병렬로 두면 높아집니다. 이 계산을 이중화가 필요한 근거로 활용하세요.
