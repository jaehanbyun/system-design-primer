:::note[핵심 요약]
- **SQL**은 정형·관계형 데이터와 엄격한 스키마를 다루고, 복잡한 조인과 트랜잭션이 필요할 때 잘 맞습니다. 확장 패턴이 명확하고 생태계가 더 확립되어 있으며, 인덱스 조회가 매우 빠릅니다.
- **NoSQL**은 반정형·비관계형 데이터와 동적이거나 유연한 스키마를 다루고, 복잡한 조인이 필요 없을 때 잘 맞습니다. 수 TB(또는 PB)의 데이터, 데이터 집약적인 워크로드, 매우 높은 IOPS 처리량이 필요할 때 유리합니다.
- 클릭스트림·로그 수집, 리더보드, 장바구니 같은 임시 데이터, 자주 접근하는 테이블, 메타데이터/룩업 테이블은 NoSQL에 잘 맞는 데이터입니다.
- 두 선택지의 차이는 아래 **한눈에 비교** 표에 기준별로 정리했습니다.
:::

## SQL을 선택하는 이유

**SQL**을 선택하는 이유는 다음과 같습니다.

- 정형 데이터(structured data)
- 엄격한 스키마
- 관계형 데이터
- 복잡한 조인이 필요함
- 트랜잭션
- 확장 패턴이 명확함
- 더 확립된 생태계: 개발자, 커뮤니티, 코드, 도구 등
- 인덱스를 이용한 조회가 매우 빠름

## NoSQL을 선택하는 이유

**NoSQL**을 선택하는 이유는 다음과 같습니다.

- 반정형 데이터(semi-structured data)
- 동적이거나 유연한 스키마
- 비관계형 데이터
- 복잡한 조인이 필요 없음
- 수 TB(또는 PB)의 데이터를 저장해야 함
- 매우 데이터 집약적인 워크로드
- 매우 높은 IOPS 처리량

## NoSQL에 잘 맞는 데이터 예

NoSQL에 잘 맞는 샘플 데이터는 다음과 같습니다.

- 클릭스트림과 로그 데이터의 빠른 수집
- 리더보드나 점수 데이터
- 장바구니 같은 임시 데이터
- 자주 접근하는('핫') 테이블
- 메타데이터/룩업 테이블

## 한눈에 비교

위 목록과 [관계형 데이터베이스](/topics/database/rdbms/), [NoSQL](/topics/database/nosql/) 페이지의 내용을 기준별로 묶으면 다음과 같습니다.

| 기준 | SQL | NoSQL |
|---|---|---|
| 데이터 형태 | 정형 데이터, 관계형 데이터 | 반정형 데이터, 비관계형 데이터 |
| 스키마 | 엄격한 스키마 | 동적이거나 유연한 스키마 |
| 조인 | 복잡한 조인이 필요할 때 적합 | 복잡한 조인이 필요 없을 때 적합 (조인은 보통 애플리케이션 코드에서 처리) |
| 트랜잭션·일관성 | 트랜잭션(ACID) 지원 | 대부분 진정한 ACID 트랜잭션이 없고 최종적 일관성(BASE)을 택함 |
| 규모·처리량 | 확장 패턴이 명확함 (복제, 페더레이션, 샤딩 등) | 수 TB(또는 PB) 저장, 데이터 집약적 워크로드, 매우 높은 IOPS 처리량 |
| 조회 | 인덱스 조회가 매우 빠름 | 키-값 저장소는 일반적으로 O(1) 읽기·쓰기 |
| 생태계 | 개발자, 커뮤니티, 코드, 도구가 더 확립됨 | 그래프 데이터베이스처럼 비교적 새로워 도구와 자료가 부족한 유형도 있음 |

## 면접에서는

- 해설 대부분은 데이터 저장소를 정할 때 "SQL과 NoSQL 사이의 유스케이스와 트레이드오프를 논의해야 한다"고 짚습니다([Twitter](/system-design/twitter/), [Mint.com](/system-design/mint/) 해설 등). 선택 이유를 데이터 형태, 스키마, 조인, 트랜잭션, 규모 같은 위 기준으로 설명하세요.
- [AWS에서 수백만 사용자로 확장하기](/system-design/scaling-aws/) 해설의 "SQL로 시작하고, NoSQL을 고려하라"는 흐름이 좋은 기본값입니다. 관계형 데이터가 필요하다는 가정이면 MySQL로 시작하고, 읽기·쓰기 요청이 크게 늘면 적절한 데이터를 DynamoDB 같은 NoSQL로 옮깁니다.
- 한 시스템 안에서도 데이터마다 다른 저장소를 고를 수 있습니다. [Twitter](/system-design/twitter/) 해설은 사용자 본인의 트윗은 관계형 데이터베이스에 저장하고, 팬아웃이 많은 홈 타임라인은 쓰기가 빠른 NoSQL이나 메모리 캐시에 두는 방안을 제시합니다.
- NoSQL을 고를 때는 어떤 유형(키-값, 문서, 와이드 컬럼, 그래프)이 맞는지까지 말하고, 최종적 일관성을 받아들인다는 트레이드오프를 함께 언급하세요. ([NoSQL](/topics/database/nosql/) 참고)

## 스스로 점검하기

<details>
<summary>엄격한 스키마, 복잡한 조인, 트랜잭션이 모두 필요하다면 SQL과 NoSQL 중 무엇이 맞나요?</summary>

SQL입니다. 정형·관계형 데이터, 엄격한 스키마, 복잡한 조인, 트랜잭션은 모두 SQL을 선택하는 이유에 해당합니다. 확장 패턴이 명확하고 생태계가 더 확립되어 있다는 점도 장점입니다.

</details>

<details>
<summary>클릭스트림 로그를 빠르게 대량으로 수집해야 한다면 어느 쪽이 맞고, 그 이유는 무엇인가요?</summary>

NoSQL입니다. 클릭스트림과 로그 데이터의 빠른 수집은 NoSQL에 잘 맞는 대표적인 데이터이며, 수 TB(또는 PB)의 데이터 저장, 데이터 집약적인 워크로드, 매우 높은 IOPS 처리량이 필요한 상황은 NoSQL을 선택하는 이유에 해당합니다.

</details>

<details>
<summary>NoSQL에 잘 맞는 데이터의 예를 다섯 가지 들어 보세요.</summary>

클릭스트림과 로그 데이터의 빠른 수집, 리더보드나 점수 데이터, 장바구니 같은 임시 데이터, 자주 접근하는('핫') 테이블, 메타데이터/룩업 테이블입니다.

</details>

<details>
<summary>SQL은 "확장 패턴이 명확하다"는데, 구체적으로 어떤 패턴을 말하나요?</summary>

관계형 데이터베이스를 확장하는 잘 알려진 기법들, 즉 마스터-슬레이브 복제, 마스터-마스터 복제, 페더레이션, 샤딩, 비정규화, SQL 튜닝을 떠올리면 됩니다. 각 기법의 장단점은 [관계형 데이터베이스](/topics/database/rdbms/) 페이지에서 다룹니다.

</details>
